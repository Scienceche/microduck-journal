- sim-to-real：BAM 舵机物理 + 域随机化（CoM ±15mm、质量 ±5%、编码器偏置、随机推力）

## 插曲：IMU 看门狗"未生效"排查（同日 01:00）

用户报看门狗没生效、现象依旧。排查结论：

1. **根因：板上烧的一直是无看门狗的旧固件**。面板 `flash_imu()` 烧
   Radxa 上 `/root/imu_fw/build/imu_to_dxl.elf`（通用名），那个文件是
   **10-10 22:16** 构建的；IWDG 代码 10-21 才写，IWDG 版 elf 只存在 PC，
   从未上板。之前"J-Link 烧录"实际没有成功或没烧对文件。
2. 固件缺陷修正：`IWDG_PR=4` 是档位（÷64）不是注释以为的 ÷32 → 改
   PR=3（÷32），超时回到设计的 1.5s。
3. **新增可验证的复位诊断**（控制表 144-151 空闲区）：
   - 144=复位原因（RCC_CSR 映射，bit0 IWDG；注意 **G0 的 CSR 偏移是 0x60**
     不是 F4 的 0x94，已对官方 stm32g031xx.h 核对）
   - 145=IWDG 复位计数（`.noinit` RAM 段 + magic，看门狗复位保 SRAM 跨复位累加，
     断电清零；链接脚本补了 .noinit 段）
   - 146=看门狗测试（写 0xA5 → 固件停喂 → ~1.5s 应复位）
4. **烧录通道换 J-Link + PC 端 OpenOCD**（Radxa 的 ST-Link 不在位）：
   xpack-openocd-0.12.0 便携版放 `C:\duck_work`，`interface/jlink.cfg` +
   `target/stm32g0x.cfg`，program verify 一把过。芯片 IDCODE 0x466 =
   STM32G03x（正经芯片，IWDG 无恙）。
5. **在线自证通过**：面板新端点 `/api/imu_wdt` + IMU 页「🐕 看门狗测试」按钮
   ——写 0xA5 → 3s 后 flags bit0=1、计数 +1。实测两连：0→1→2。
   面板 IMU 页现在常显"上次复位原因 + 看门狗复位次数"。
6. 顺带修复：`duck_policy.py` 的 IMU_BLOCK_ADDR 笔误 0x36 → 124（0x7C），
   已重新部署 Radxa。
7. 机制确认：`spi_xfer`/`board_bus_write` 是无超时死等——bus_tx 卡在 TC
   死等时 DE 拉住整条总线（这正是"总线扫不出来"的形态），主循环停喂，
   IWDG 1.5s 复位释放总线。看门狗激活后此类挂死应自愈，无需再断电池。

固件源已同步 Radxa `/root/imu_fw`（面板烧录按钮以后烧的就是带诊断的新版），
产物备份 `工具/imu_to_dxl_wdt2_diag.elf`。

### 总线硬件诊断链（最终定案：Radxa 侧 TX 不上线）
1. 上电后总线全体沉默；扫描"全 ID 应答"实为 **Radxa 串口自回环**（ping 不存在的
   id50 也成功 = 假阳性，ping 不可作判据，必须内容校验读）。
2. Radxa 自动重启过两次（08:18/08:29，怀疑上电浪涌/内核问题）。
3. **SWD 判别链**（openocd+J-Link 直读 IMU 板）：
   - RCC_CSR 无 IWDG 复位 → 不是复位循环
   - g_table RAM 显示 v2.2 在跑、g_ms 精确走秒 → 主循环活
   - GPIOA ODR bit1=1 → DE 已释放
   - **Radxa 连发 30 帧 ping 期间 IMU 板 g_rx_w 纹丝不动** → Radxa 的 TX
     根本没驱动到总线数据线
   - 静默时线路干净（无 0x00 噪声）→ 不是被钳位，是**断路/Radxa 侧收发器坏**
4. 结论：嫌疑集中在 **Radxa HAT 的总线收发器（或 HAT-总线接线）**，待用户断电
   物检（重插接线/看芯片烧痕/或用 USB-TTL 临时换路 /dev/ttyUSB0）。
5. v2.2 固件（5s 心跳信标 + USART ISR 错误标志清刷）已烧录——心跳为今后
   TX 卡死类故障提供自愈与可观测性。

### 教训沉淀
- ping 类探测在半双工总线上会被回环骗过：**判据必须内容校验**（版本号/数值合理性）。
- SWD 直读 RAM/外设是终极诊断（uptime 走秒、队列指针、CSR 标志），比盲猜快十倍。
- Radxa 会话/后台任务在长时间空闲后可能被清理——过夜训练要预期中断、用小间隔
  checkpoint 续跑。
