# 调试记录 2026-11-06～08：短叫/长叫三连症结 · 嘴方向反 · 音库缺件 · 播放设备名坏

## 症状（用户原话）

> 点鸭子中控台的短叫和长叫，鸭嘴只会张开一点，声音发出一点点。
> 按住不放也不行。……下颌摆动是往上的。……声音不咋样大。

最终 11-08 验收：**嘴向下开满行程、长叫持续、音量明显增大，全部正常**（验收方式：用户听感+目视；当轮进程监控因 ssh 转义问题未捕获，进程级证据以 `robotctl quack` 僵尸 + 直连 PLAY_OK 为准）。

## 最终结论（一句话版）

1. **嘴只张一点** = 34 号舵机标定 `direction=+1` 装反 → "张开"指令让下颌**向上顶死上喙**，2.46° 旷量处堵转（负载 -600、误差恒 -27.5°）。改 `direction=-1` 后痊愈。
2. **长叫响一下就停** = 官方音库缺 `wheee_{start,loop,end}_*.wav` 三件套，`sound.rs` 走 `degraded_wheee()` 降级路径：播一遍一次性音效即止（`robotd/src/sound.rs:696-705,724-741`）。R17"安装/修复"的 `--prepare` 阶段已补齐。
3. **声音小** = 三因叠加：robotd 播放设备名 `plughw:aic3104` 在本机不存在（aplay 直接打不开）；TLV320 HAT 是 dummy-codec + I2C 用户态控制，**没有 ALSA 音量控件**（官方 `PCM Playback Volume` 路线在此硬件上不可能）；且 codec 重启复位、从来无人开机重初始化，增益一直是脚本默认 -32dB。

## 三次误诊（教训都在这）

### 误诊 1：怪用户用法（11-06 晚）
- 首诊认为是"点按 vs 按住"用法问题 + 嘴巴滑条限制。**用户实测按住 5 秒依然不行**，滑条本来就是 100%。
- 教训：**先测量再建议**。监控数据（快照 10Hz）显示按住期间嘴目标角度全程保持 30° 达 4.86 秒——输入链路完全无辜，一步洗清浏览器→中控台→SSH→remote_input→robotd 整条路。

### 误诊 2：机械堵转 = 机械异物（11-06 晚）
- 合成 6.7 秒按住的数据：目标 30°、实测卡死 2.46°、误差恒定、负载恒 -600 → 我判定"机械阻挡，查弹簧/毛刺/走线"。
- 真相（11-08 用户目视）：**下颌往"上"摆**——方向反了！堵转是真的，但堵的是"错误方向撞上喙"，不是异物。改一行标定痊愈，机械无损。
- 教训：**舵机顶死 ≠ 有障碍物，也可能是方向反了在撞限位**。遥测永远分不清"向上顶死"和"向下顶死"，**眼睛的一秒观察 > 一小时数据**。方向可疑时先手动轻推验证，别拆机器。

### 误诊 3：音量走官方路线（11-08）
- 第一次：跑 R17"安装/修复"，`--system` 阶段失败——`alsactl store aic3104` 退出码 19（卡不存在）。原因：`robotd.toml` 的 `["audio"]` 段没写 device，`voice-setup.py` 回退官方默认卡名。
- 第二次（用户手跑 sed）：**静默失败**——配置器写的 TOML 段头/键全带引号（`["audio"]`、`"device" = ...`），`sed '/^\[audio\]/'` 根本不匹配。
- 第三次：正确改到 `plughw:HATTLV320` 后，官方路线依然不通——`amixer -c HATTLV320` 只有 SoC I2S3 路由控件，**没有 PCM Playback Volume**（TLV320 由 I2C 寄存器控制，`/root/audio/tlv320_init.py` 才是本机音量旋钮）。彻底放弃官方音量通道，改走旧栈增益路线。
- 教训：复刻硬件 ≠ 官方硬件，**安装器的硬件假设（aic3104 声卡 + ALSA 控件）在本机两条都不成立**；改配置前先 `cat` 看一眼真实格式（带引号的 TOML 键）。

### 降丢包算法清单（按性价比排序）
1. **重部署 11-05 构建**（恢复热修复2/3）→ 回到 0.004%。必做，零风险（已验证过的二进制）。
2. **分 train（split-train）**：一次 16 设备 sync read 拆成按物理分支的 2-3 段（右腿[10-14] / 左腿[20-24] / 头颈[30-34]，IMU 各段首），段间 ~200µs 总线静默。跨分支边界（34→10 这种）结构性消失。周期预算：现 train ~3.5ms，拆 3 段 +gap ≈ 4.5ms ≪ 20ms。改动点：`duck-control/src/feetech.rs` `telemetry()`，~15 行。
3. **同周期定点重试**：`allow_partial` 读到缺谁，立刻对缺的 ID 单独补读（短 deadline），成功则本周期满数据，失败才 coast。把"每 1.7% 周期丢一帧"变成"几乎不丢"。改动点：`feetech.rs` `sample()` 失败分支，~10 行。
4. **边界矩阵探针 + Held-Karp 最优排序**：停机窗口跑 `boundary_probe.py`（本记录同目录工具），实测 15×15 有序相邻对故障率，DP 求最小故障 Hamiltonian 路径作为请求顺序——把手工换序升级为数据驱动最优。顺带验证分 train 分组。
5. **标定模式容错**：`feetech_commissioning.rs:951` 附近，单次读失败改为连续 3 次才 abort（对齐运动模式 consecutive 语义）。
6. **降波特率对照实验**：`model.rs:50` BAUD_RATE 1M→500k，train 时间翻倍仍 ~7ms<20ms，抗反射裕量翻倍。一行改动，作对照。
7. 硬件层（社区标准做法）：数据线单点上拉偏置 4.7–10kΩ（稳定空闲高电平、助 turnaround 边沿）；头支（J_NECK/J_HEAD）末端端阻或缩短桩线；J_R/J_HEAD 接插件重新压接；必要时磁环。终极方案：自制板做"智能中继"（每分支 store-and-forward 重定时，结构消灭边界翻转——社区 RP2040 repeater 思路， imu_to_dxl 的板厂能力足够做）。

### 边界矩阵探针实测（11-08 晚，补完）

- 工具 `boundary_probe.py` 上机过程踩了 4 个坑，全修后 20 秒跑完 210 对×100 次：**预检 15/15，全矩阵 21000 笔交易零故障**。
- 踩坑清单（教训）：① 校验和误把帧头 FF FF 计入且漏长度字节；② 修和时漏改指令字节——**FT5 的 SyncRead=0x82**（0x02 是普通 READ，广播 0x02 无应答）；③ `cat|ssh` 管道偶发 0 字节上传（改 scp）；④ 多个探针实例与 robotd 抢串口（IO 层统一用 exclusive=False + tty.setraw + in_waiting 轮询——这套在本机验证过）。
- **关键负结果**：两设备最小列车下，任何相邻对都打不出边界故障（含 34→10/34→11）→ 线上那 ~0.07% 的残余故障**不是纯"对属性"，需要完整 16 设备列车上下文**（前应答尾巴的排空、IMU 大块、负载电压跌落等叠加）。因此：Held-Karp 排序在最小对上无信号（全零权重，排序输出无意义）；真正对路的算法是**分 train**（拆散列车上下文）与**同周期定点重试**（兜住残余），而不是继续换序。
- 附带收获：busStatus 里 robotd 用 `serialport` crate 的发送=普通 write（"HAT 方向自动"），pyserial 需手动 `tty.setraw` 才等效；FT5 应答帧 21B（FF FF id 11 00 + 15 数据 + sum），解析器在 `feetech.py:117` 有现成参考实现。
