## 0. 一图看懂全流程

```
改东西(质量/奖励/锚点) → 热启动微调 → 多点位评测 → 双专家重组 → 导出+保真校验
      → 打包(哈希链) → OTA部署 → 真机验收
```

**不是所有改动都要训练**（先看这张表，省一天）：

| 你改了什么 | 要训吗 |
|---|---|
| 电压/姿态阈值/技能时长（manifest.json、robotd.toml）| ❌ 重启 robotd 即可 |
| gate 的 c0 等门控参数 | ❌ 改 checkpoint 一个数（见 fix_c0.py）|
| 仿真质量/几何/关节限位 | ✅ 微调双专家 |
| 奖励/锚点/桥接桶（训练目标）| ✅ 通常从头训更稳（如 run14）|
| 只是换了个 checkpoint 点位 | ❌ 重组即可 |

## 1. 开训前的三道检查（5 分钟，跳过必踩坑）

### ① 内存检查（2026-11-22 事故：提交内存 97% → OpenBLAS 分配失败）

```powershell
# PowerShell: 看"已提交/上限"，超过 90% 先关大程序
(Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit').CounterSamples
```

大户名单（实测）：bambu-studio、KiCad、多个 VS Code 窗口。腾出 ≥8GB 提交额度。

### ② 确认用哪个入口（2026-11-22 事故：`python -m` 不认 `--init-checkpoint`）

```bash
cd C:/duck_work/microduck_rl
# 对：console script（--init-checkpoint 是它在 argparse 前拦的）
./.venv/Scripts/train.exe <任务名> --init-checkpoint <ckpt路径>
# 错：python -m mjlab.scripts.train  ← 报 Unrecognized options
```

### ③ wandb 离线（2026-11-22 事故：没登录直接 UsageError 崩）

训练命令永远带上 `WANDB_MODE=offline`（本地照记 tfevents，不用 wandb 账号）。

## 1.5 双 Agent 交叉协议（2026-11-23 起强制）

> 来源事故：同一个人既发训练又写监控哨兵，结果哨兵盯错目录、正则误伤、
> 三次误报"训练死亡"，实际训练活着——**自己审自己 = 没审**。

**角色分工**：

| | 训练实施 Agent | 自检 Agent（独立）|
|---|---|---|
| 职责 | 改配置、发训练、收割 checkpoint | 发车前核验 + 运行中审计 |
| 禁止 | 自己给自己出 PASS | 碰训练进程/配置（只读）|
| 判据 | — | 每项 PASS/FAIL 必须带证据原文 |

**三道闸门**：

1. **发车闸**（训练启动前）：自检 agent 核验——XML 是否落盘（grep 原文）、
   warm-start checkpoint 存在且路径正确、内存/显存余量、无残留训练进程、
   任务名与意图一致。全 PASS 才许 launch。
2. **运行闸**（每 ~10 分钟或收割前）：自检 agent 独立读日志迭代数（隔 60s 两读
   必须增长）、确认 checkpoint 真在落盘、进程唯一。**判断训练死活的唯一可信源
   是日志迭代数，不是 tasklist**（进程检测跨会话不可靠，已三次误报）。
3. **收割闸**（取 model_N 前）：自检 agent 确认目标 checkpoint 文件存在、
   修改时间新鲜、目录是本次 run（ls -t 会拿到僵尸目录，必须按 mtime 逐个验）。

**哨兵编码守则**（血泪换的）：
- 错误检测正则禁止匹配 `error_vel`/`terrain` 等指标名单词——用完整短语
  （`out of memory`、`Unrecognized options`、`Traceback`）
- 监控目录不要 `ls -t | head -1` 猜——从训练日志里读出 run 目录名再盯
- 杀进程后等 GPU 释放（nvidia-smi 确认）再重启，否则建图 OOM

## 2. 训练命令模板

### 场景 A0：同任务物理适配续训（⚠️ 2026-11-23 新增，先看这条！）

**改了质量/物理参数、任务不变、想保留原有行为能力** → 用**普通 resume**
（`--init-checkpoint` 但**不加** `MICRODUCK_WARM_START`）：

```bash
WANDB_MODE=offline ./.venv/Scripts/train.exe Mjlab-Velocity-Rough-Backlash-MicroDuck \
  --init-checkpoint logs/rsl_rl/velocity/<旧run>/model_3999.pt
# 验证: 日志里【不】出现 "common_step_counter N → 0" 行, 迭代号从旧值续起
```

**为什么不能用 warm start**（2026-11-23 事故实证）：Patch 5 会把课程计数归零——
速度指令课程从头爬，2000 迭代都在练低速站立，**行走专家被练成站桩**
（前进 avg_vx 0.155→0.001）。warm start 是为**跨任务**设计的；同任务续训
要的就是课程连续性。

### 场景 A：跨任务热启动微调（旧场景，慎用）

```bash
cd C:/duck_work/microduck_rl

# 站立/起身专家（StandUp 任务）
WANDB_MODE=offline MICRODUCK_WARM_START=1 ./.venv/Scripts/train.exe \
  Mjlab-StandUp-Rough-Backlash-MicroDuck \
  --init-checkpoint logs/rsl_rl/microduck_stand/<旧run目录>/model_500.pt

# 行走专家（Velocity 任务）
WANDB_MODE=offline MICRODUCK_WARM_START=1 ./.venv/Scripts/train.exe \
  Mjlab-Velocity-Rough-Backlash-MicroDuck \
  --init-checkpoint logs/rsl_rl/velocity/<旧run目录>/model_3999.pt
```

两个环境变量各管什么：
- `MICRODUCK_WARM_START=1`：加载旧权重/归一化器但**课程计数归零**（不归零会跳课，
  2026-09-09 事故：第 1 迭代就全难度）。同时自动跳过优化器加载（双专家参数量不同）。
- `WANDB_MODE=offline`：见上文坑③。

**成功的标志**（日志里找这行）：
```
[mdp] Patch 5: WARM START from ... — common_step_counter 12024 → 0 ...
Learning iteration 0/15000
```

### 场景 B：从头训（改了奖励/锚点，如 run14 蹲姿头锚点）

```bash
WANDB_MODE=offline ./.venv/Scripts/train.exe Mjlab-StandUp-Rough-Backlash-MicroDuck
# 没有 --init-checkpoint 和 MICRODUCK_WARM_START
```

### 关键认知：默认 15000 迭代几乎总是太长

| 专家 | 甜蜜点 | 过训后果（真实数据）|
|---|---|---|
| 站立/起身 | **@500 左右** | @1999 起身从 100% 掉到 75%（run14 实测，2026-11-18）|
| 行走 | @2000-4000 | 步态漂移 |

实操：训到 1000 就够选点了。哨兵接力写法（stand 到 1000 自动切 walk）：

```bash
until ls logs/rsl_rl/microduck_stand/<新run目录>/model_1000.pt >/dev/null 2>&1; do sleep 30; done
taskkill //F //IM train.exe   # 掐掉 15000 的长跑
# 然后立刻发场景A的第二条命令
```

速度参考：~1.4s/迭代 → 1000 迭代 ≈ 25 分钟（RTX 4080 级显卡）。

## 3. 训完：评测选点（必做，别信最终迭代）

用六批次起身评测对比**新旧 checkpoint**（判据=不退化才能上线）：

```bash
cd C:/duck_work/microduck_rl
./.venv/Scripts/python.exe C:/duck_work/eval_getup.py \
  "logs/rsl_rl/microduck_stand/<新run目录>/model_500.pt"
# 结果在 eval_getup_results.json，六个批次：俯卧/仰面/桥式/后仰接手/坐姿/站立对照
# 合格线（对齐 run13@500 基线）：100/100/75/100/100/100
```

**同一评测跑两遍看方差**（64env 批次 ±8% 正常；差异大于此=点位不稳，换点）。

行走专家评测：`eval_walk.py` 同理（前进速度/存活/稳定性三指标）。

## 4. 双专家重组（P2.x 系列配方）

改哪个专家就换哪个，另一个**逐位不动**（最小差异原则，出问题好定位）：

```bash
# 参照 make_p292_checkpoint.py：底座=现役 checkpoint，只换 stand_expert.* + stand_normalizer.*
# 三个断言必须全过：walk/gate 逐位==底座、stand==新权重、无残留键
./.venv/Scripts/python.exe make_p292_checkpoint.py   # 复制成 make_p293_*.py 改路径
```

gate 参数在底座里自带（P2.9.x 应保持 `c0=0.10`，2026-11-16 修的小步病，别丢）。

## 5. 导出 + 保真校验（2026-11-18 的坑全在这）

```bash
./.venv/Scripts/python.exe export_p292.py   # 复制成 export_p293.py 改路径
```

保真校验**必须做**（导出图是 batch=1，且 TensorDict 取法有坑）：

```python
# 同一条展平观测喂 PT 和 ONNX，逐 env(batch=1) 比动作
# 合格：max diff < 1e-4（实测 2.9e-06）
# 坑1: ONNX 图定死 batch=1，8env 的 obs 要逐条喂
# 坑2: obs 是 TensorDict，用策略自己的 _get_flat_obs 产输入才逐位一致
```
