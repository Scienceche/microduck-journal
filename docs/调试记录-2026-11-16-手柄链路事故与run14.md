## 事故分析（为什么"按键有效摇杆无效"指向轴映射而非蓝牙）

读 `gamepad-r7/gamesir-xboxd.c` 源码：

1. 桥启动时 `EVIOCGABS` 抓取每个源轴的 min/max（`add_axis`），
   并用**当时的静止值**给轴排序挑左右摇杆（`axis_center_error`/`sort_by_center`）、
   推断扳机方向（`add_trigger_axis` 读 `info.value`）。
2. **轴映射只在启动时构建一次**。若桥启动时手柄 HID 处于半重连的脏状态
   （值域被压缩/轴序错乱），选错源轴或抓错量程后，全推摇杆 → 输出只有轻微变化。
3. 按键是位映射不走这套逻辑 → 按键照常工作。
   ——与用户症状完全吻合。
4. 21:00 的 `udevadm trigger` 重建全部输入节点 + 多次桥重启，
   恰好在手柄半连接状态下重建了轴映射 → 播下祸根。
   之后 AIC8800 每次重连 HID 会话劣化，映射愈发不对。

## 教训（写给下个会话）

1. **udev 规则任何改动都等于动输入设备枚举顺序**——在工作系统上先快照再改，
   改完必须验证全链而不是只看服务绿色。
2. `udevadm trigger` 在带蓝牙 HID 的系统上等于对活跃 HID 会话做心脏复律，
   能不做就不做；要做先断开手柄。
3. 桥的轴映射 = 启动时一次性抓取。**重启桥必须发生在手柄完全就绪之后**。
4. "按键有效摇杆无效" ≠ 蓝牙死。先查轴映射层再怀疑芯片。

## 补记 6（2026-11-19 IMU 仪表排障：写超时三重奏）

**症状**：仪表页 3D/瀑布全黑不动。
**排障链**（每步有证据）：
1. ws 通路 OK（自建 WebSocket 收到 hello/stats）但 **sample 帧为零** → 病在服务端
2. /api/state 计数冻结陷阱：早先读到的 polls=32666 ok=32666 是**旧会话历史**，
   重连后归零才暴露真面目：ok=0 + err='Write timeout'
3. 重启服务无效、拔 USB 无效 → 最终服务重启后用户页面自动重连成功：
   ok=416/416 @100.2Hz 数据恢复（写超时为 UART 卡死态，彻底重启序列后释放）
**教训**：
- 读 /api/state 计数必须**间隔两次看增量**，单次快照会被冻结历史值骗
- 页面带 ws 自动重连（1s 退避），服务重启后会自己把会话拉起来——排障时记得这层
- 硬件半双工总线上任何"调试接口"外接（USB-TTL）都可能顶住线路 → 写超时
**IMU 状态结论**：总线通、板应答、SFLP 数据流 100Hz 正常（md1 人格块 @124）。
config 的 vendor 区 160+20 读 0x08=ERR_RANGE 属预期（板无此区），不影响数据。

## 补记 7（2026-11-19 欧拉角平线破案：人格错配）

**症状**：陀螺 xyz 有数，roll/pitch/yaw 平线。
**证据链**：样本帧 quat_raw 冻结 → flags 恒 0（quat_valid=False ready=False）→
bus.py md1 解码逻辑自洽 → 对照固件身份字：板子是 **FT6 固件**（06 00 00 00 F2，
model 0xF210 fw 6.0），服务却用默认 md1 人格解码 → 布局错位。
**修复**：`/etc/systemd/system/imu-scope.service.d/personality.conf` 加
`Environment=SCOPE_FEE_PERSONALITY=ft6` → daemon-reload → 重启 →
quat_valid=True / |q|=1.000 / euler 实时。
**教训**：
1. bus.py 自带人格机制（native/ft6/md1），设备身份字一读便知该用哪个——
   **连接前先验身份**，别信默认
2. "传感器数据在但派生值死"= 解码层错位的典型指纹（原始量偏移恰好命中、结构体错位）
3. 中途的 SFLP 疑惧、reboot 无效全是错位幻觉；vendor 0x08 是长度不匹配装饰性报错
